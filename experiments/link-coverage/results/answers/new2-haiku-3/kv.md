The paper is **Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention" (2023)**, which introduces vLLM. It's the only paper in the library that covers KV cache mechanics in depth. I read the text layer and didn't use a note, since none exists for it yet.

## How the KV cache works

- **Why it exists:** Generation is autoregressive. Each new token attends to the keys and values of every earlier token. The model computes those once per token and stores them, so each step only computes the new token's key and value and reads the rest from memory ([p. 3](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=3&rect=90,360,295,398) gives the attention formula). The prompt phase is a parallel matrix multiply. The decode phase is sequential and memory-bound.
- **How big it is:** Per token, it's 2 (K and V) × layers × hidden size × bytes per value. The paper's example is OPT-13B: 2 × 40 × 5120 × 2 bytes ≈ 800 KB per token, so a 2048-token request needs about 1.6 GB ([p. 4](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=4&rect=242,345,295,356)). On an A100-40GB, weights take 65% of memory and the KV cache about 30% ([p. 1](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=1&rect=431,607,509,618)). The cache, not compute, caps the batch size.
- **The problem with existing systems:** They reserve one contiguous chunk per request, sized for the maximum length, and the output length isn't known in advance. Only 20.4–38.2% of that reserved memory held real token states ([p. 2](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=2&rect=195,660,239,671), Fig. 2).
- **The fix (PagedAttention):**
  - Split each request's KV cache into fixed-size blocks, 16 tokens by default ([p. 12](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=12&rect=409,672,547,683)).
  - Keep a block table mapping logical blocks to physical GPU blocks, and allocate a block only when the last one fills ([p. 6](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=6&rect=87,196,127,206), Fig. 6).
  - The attention kernel runs block by block, so the blocks don't need to be contiguous ([p. 5](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=5&rect=344,261,559,300), Eq. 4).
  - Share blocks with reference counts and copy-on-write. Parallel samples and beam candidates share their prompt, and shared blocks are copied only when one sequence writes to them ([p. 7](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=7&rect=261,417,296,428), Figs. 8–9).
- **When memory runs out:** Evict a whole sequence at a time, then either swap its blocks to CPU RAM or recompute them later ([p. 8](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=8&rect=317,453,439,463)). Section 7.3 compares the two.

## What was measured

- **Setup** ([p. 10](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=10&rect=317,595,374,605); [Table 1, p. 9](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=9&rect=77,73,271,155)): OPT-13B, 66B and 175B, plus LLaMA-13B, on A100 GPUs. Workloads are ShareGPT and Alpaca with Poisson arrivals.
- **Main metric:** normalized latency, the mean end-to-end latency divided by output length. Throughput is the request rate a system sustains before latency explodes.
- **Results:**
  - Headline: 2–4× throughput over FasterTransformer and Orca at the same latency ([p. 1](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=1&rect=239,352,295,362)).
  - ShareGPT: 1.7–2.7× the request rate of Orca (Oracle), and 2.7–8× that of Orca (Max) ([p. 11](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=11&rect=251,433,295,443)).
  - OPT-13B: 2.2× more concurrently batched requests than Orca (Oracle), and 4.3× more than Orca (Max) ([p. 11](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=11&rect=120,505,182,515)).
  - Sampling: sharing gives larger gains for beam search than for parallel sampling ([p. 11](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=11)).
- **Costs:** The paged attention kernel is 20–26% slower than FasterTransformer's attention kernel, but end-to-end it still wins ([p. 12](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=12&rect=371,408,402,419)). Block size trades GPU parallelism against fragmentation.

## Caveats

- Baselines are 2023 systems (FasterTransformer, Orca). Orca (Oracle), which assumes known output lengths, is an upper bound that isn't achievable in practice.
- The paper's own accuracy claim is that the output is unaffected by the change.
- The paper doesn't cover KV quantization or cross-request prefix reuse beyond the shared-prompt case, so look elsewhere for those.
