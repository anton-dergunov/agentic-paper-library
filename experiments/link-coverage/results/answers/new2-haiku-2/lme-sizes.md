The paper defines only two standard sizes, **S** and **M**. They differ in how much chat history the model must search, not in the questions.

- **LongMemEval_S** (about 115k tokens per question, p. 5): each question's evidence sessions are placed in the middle of unrelated chat sessions. The filler comes from simulated self-chats and from public user-AI data (ShareGPT, UltraChat), and every session gets a timestamp. This is roughly the size a long-context model can read in one prompt. [p. 5](http://pdf.invalid/llm/memory/benchmarks/LongMemEval.%20Benchmarking%20Chat%20Assistants%20on%20Long-Term%20Interactive%20Memory.pdf?page=5)
- **LongMemEval_M** (500 sessions, about 1.5M tokens, p. 5): the same design with a much longer history, far beyond the context windows of the models tested. It is meant to force a memory or retrieval system rather than full-context reading. [p. 5](http://pdf.invalid/llm/memory/benchmarks/LongMemEval.%20Benchmarking%20Chat%20Assistants%20on%20Long-Term%20Interactive%20Memory.pdf?page=5)

The paper also uses a third setting, **Oracle**, which is not a size. The model sees only the evidence sessions, so it measures reading ability without any search. Comparing Oracle with S shows the drop caused by the surrounding haystack, for example 0.870 to 0.606 for GPT-4o with direct reading. [p. 6](http://pdf.invalid/llm/memory/benchmarks/LongMemEval.%20Benchmarking%20Chat%20Assistants%20on%20Long-Term%20Interactive%20Memory.pdf?page=6)

Other versions: the paper says the pipeline's length is "freely extensible" but names only S and M as standard settings. It does not describe any other released versions, and I can't confirm any later releases from this library. If you want those, check the benchmark's own repository rather than this paper.
