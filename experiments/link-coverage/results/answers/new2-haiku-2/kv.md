**Short answer:** the KV cache stores each token's attention keys and values so they aren't recomputed at every decoding step. It grows with every token of every request, so how you allocate it decides how many requests fit in GPU memory, and therefore your throughput.

The library has one paper that covers this in depth: **Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention" (SOSP '23, arXiv 2309.06180; vLLM)**. It's a serving-systems paper, so the KV-cache mechanics are background to its main contribution. I grepped the library and found no other paper on KV caching.

## How it works

1. **Why it exists.** A Transformer generates one token at a time, and each new token attends to the keys and values of all earlier tokens. Storing those keys and values means each step only computes the new token's entries. ([p. 1](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=1); [p. 4](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=4))

2. **Size per token.** For OPT-13B in FP16, the paper gives 2 (K and V) × 5120 (hidden size) × 40 (layers) × 2 bytes ≈ 800 KB per token. A 2048-token request can need 1.6 GB ([p. 4](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=4&rect=242,345,295,356)). The general formula is `2 × layers × hidden_dim × bytes`, which is for plain multi-head attention; grouped-query attention shrinks it. That formula is my addition, not the paper's.

3. **Where the memory goes.** On an A100-40GB serving a 13B model, weights take about 65% and the KV cache about 30%. The KV cache is the part that varies with load ([Fig. 1, p. 1](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=1&rect=317,177,560,409)). Table 1 gives 12 GB for the KV cache, which holds 15.7K token slots ([Table 1, p. 9](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=9&rect=77,73,271,155)). That matches 12 GiB ÷ 800 KB, so the GB there are binary.

4. **The problem with existing systems.** They reserve one contiguous chunk per request, sized for the maximum length. That causes reservation waste, internal fragmentation, and external fragmentation. Only **20.4%–38.2%** of the reserved KV memory held real tokens ([Fig. 2, p. 2](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=2&rect=54,71,295,244); [text](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=2&rect=195,660,269,671)). Less waste means a bigger batch.

5. **PagedAttention, the fix.** Each sequence's KV cache is split into fixed-size blocks of B tokens, which need not be contiguous in memory. A block table maps logical blocks to physical ones, and blocks are allocated only when needed, like OS pages. The attention sum is computed block by block:

   $$A_{ij} = \frac{\exp(q_i^\top K_j/\sqrt{d})}{\sum_{t=1}^{\lceil i/B\rceil} \exp(q_i^\top K_t/\sqrt{d})}, \qquad o_i = \sum_{j=1}^{\lceil i/B\rceil} V_j A_{ij}^\top$$

   ([Eq. 4, p. 5](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=5&rect=344,261,559,300)). Here $q_i$ is the query for token $i$, $K_j, V_j$ are the keys and values in block $j$, and $d$ is the head dimension. The kernel fetches blocks one at a time, so they don't need to be adjacent.

6. **Sharing.** Sequences can share blocks: the prompt in parallel sampling, and common prefixes in beam search, using copy-on-write when a shared block diverges ([p. 4](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=4&rect=162,708,278,718)).

## Measurements

- **Metric:** normalized latency, the mean end-to-end latency divided by output length, at increasing request rates. Throughput is the highest rate that keeps latency low ([p. 10](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=10)).
- **Setup:** OPT-13B, 66B and 175B, plus LLaMA-13B, on A100 GPUs. Workloads are ShareGPT (long conversations) and Alpaca (short instructions), with Poisson arrivals ([Table 1, p. 9](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=9&rect=77,73,271,155); [p. 10](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=10)).
- **Headline:** vLLM improves throughput **2–4×** over FasterTransformer and Orca at the same latency ([p. 1](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=1&rect=54,364,210,374)).
- **Request rates:** on ShareGPT, vLLM sustains **1.7–2.7×** the rate of Orca (Oracle) and **2.7–8×** that of Orca (Max) at similar latency ([p. 11](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=11)). For OPT-13B, vLLM batches **2.2×** more requests than Orca (Oracle) and **4.3×** more than Orca (Max) ([p. 11](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=11&rect=120,505,244,515)).
- **Sharing:** memory saved by block sharing is **6.1–9.8%** for parallel sampling and **37.6–55.2%** for beam search ([Fig. 15, p. 11](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=11)).
- **Block size:** 16–128 tokens work best on ShareGPT ([p. 12](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=12)).

**Caveats:** the baselines are the authors' own re-implementations. Orca is not public, so they built three variants with different over-reservation policies ([p. 10](http://pdf.invalid/ml-systems/inference-and-serving/Efficient%20Memory%20Management%20for%20Large%20Language%20Model%20Serving%20with%20PagedAttention.pdf?page=10)). The gains depend on long, variable-length workloads and on sharing, so they are smaller on short-sequence workloads like Alpaca. The 2–4× figure is a best case, not a universal speed-up.
